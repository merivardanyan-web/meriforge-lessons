02Գաղտնիքները պահոցում չեն

JS Դաս 17-ում սովորեցիր .gitignore։ Այնտեղ ամենավատ բանը, որ կարող էր հայտնվել պահոցում, node_modules-ն էր։ Այստեղ դա .env-ն է՝ բազայի գաղտնաբառով և APP_KEY-ով։

.gitignore — Laravel-ը այն ստեղծում է ինքը (հատված)
/vendor           # composer install-ը կվերականգնի
/node_modules
/public/storage   # symlink, storage:link-ը կստեղծի
.env              # ⭐ գաղտնիքներ
.env.backup
.env.production
# ...
ստուգում․ .env-ը երբևէ commit արվե՞լ է
# Ներկայիս վիճակը. պետք է լինի դատարկ
git ls-files .env

# ԱՄԲՈՂՋ պատմությունը. պետք է լինի դատարկ ⭐
git log --all --oneline -- .env

# Գաղտնաբառեր կոդում (օրինակ՝ config/database.php-ում ձեռքով գրված)
git grep -n -i "password" -- "*.php" ":!vendor"
Հարձակում․ բոտերը կարդում են GitHub-ը

Հրապարակային պահոցները անընդհատ սկանավորվում են ավտոմատ բոտերով, որոնք փնտրում են բանալիներ և գաղտնաբառեր։ Եթե .env-ը գոնե մեկ անգամ commit արվել է, պետք է ենթադրել, որ այն արդեն կարդացվել է։

Եվ ամենակարևորը․ ֆայլը ջնջելը և նոր commit անելը չի օգնում։ Հին commit-ը մնում է պատմության մեջ, և git log -p -- .env-ը ցույց է տալիս դրա պարունակությունը ցանկացածին, ով clone է անում պահոցը։

Ճիշտ արձագանքը․ փոխել գաղտնիքը (բազայի գաղտնաբառը, php artisan key:generate, API բանալիները)։ Պատմությունը մաքրելը երկրորդական է, իսկ արտահոսած գաղտնիքը մնում է վտանգավոր, քանի դեռ այն չի փոխվել։

.env.example — ի՞նչ է պահոցում
APP_NAME=TechnoMarket
APP_ENV=local
APP_KEY=                      # դատարկ — key:generate
APP_DEBUG=true
APP_URL=http://technomarket-laravel.test
APP_LOCALE=hy

DB_CONNECTION=mysql
DB_DATABASE=technomarket_laravel
DB_USERNAME=root
DB_PASSWORD=                  # դատարկ

SESSION_DRIVER=database
.env.example-ը փաստաթուղթ է

Այն ասում է նոր մշակողին (կամ քեզ՝ վեց ամիս հետո), թե ինչ փոփոխականներ են պետք, առանց ասելու դրանց արժեքները։ Դաս 21-ում ավելացրիր APP_LOCALE=hy։ Եթե այն չկա .env.example-ում, clone անողի մոտ սխալները անգլերեն կլինեն, և նա չի հասկանա ինչու։

Կանոն․ ամեն անգամ, երբ ավելացնում ես տող .env-ում, ավելացրու այն նաև .env.example-ում՝ առանց գաղտնի արժեքի։

03Production կարգավորում

.env սերվերում
APP_ENV=production
APP_DEBUG=false               # ⭐ Դաս 1, 10, 15, 17, 18 — վեցերորդ անգամ
APP_URL=https://technomarket.example.am
APP_KEY=base64:...            # key:generate ՍԵՐՎԵՐՈՒՄ, ոչ պատճենված լոկալից

LOG_LEVEL=error

DB_DATABASE=...
DB_USERNAME=...               # ոչ root
DB_PASSWORD=...               # երկար, պատահական

SESSION_DRIVER=database
SESSION_SECURE_COOKIE=true    # cookie միայն HTTPS-ով — Դաս 7
APP_DEBUG=true production-ում

Դաս 18-ում ցույց տվեցինք, որ debug ռեժիմում սխալի էջը ցույց է տալիս ֆայլը, տողը և stack trace-ը։ Production-ում դա նշանակում է՝ ցանկացած այցելու, որ կառաջացնի սխալ (օրինակ՝ բազան մի պահ անհասանելի է), կտեսնի քո ֆայլերի կառուցվածքը, SQL հարցումները և երբեմն շրջակա միջավայրի փոփոխականները։

Սա այն սխալն է, որ ամենից հաճախ հանդիպում է սկսնակների առաջին deploy-ում։ Սա նաև առաջին բանն է, որ փորձառու մշակողը կստուգի քո demo-ում։

deploy-ի հրամանները
# 1. Կախվածություններ՝ առանց dev փաթեթների, օպտիմիզացված autoload-ով (Դաս 14)
composer install --no-dev --optimize-autoloader

# 2. Միայն առաջին անգամ
php artisan key:generate
php artisan storage:link

# 3. Միգրացիաներ. --force, որովհետև production-ում Laravel-ը հարցնում է հաստատում
php artisan migrate --force

# 4. Քեշ՝ config, routes, views, events
php artisan optimize

# Ստուգում
php artisan about
optimize-ից հետո env()-ը վերադարձնում է null

php artisan optimize-ը (և config:cache-ը) միավորում է բոլոր config/*.php ֆայլերը մեկ քեշավորված ֆայլում և այլևս չի կարդում .env-ը։

Եթե կոնտրոլերում կամ seeder-ում գրել ես env('ADMIN_EMAIL'), լոկալ այն աշխատում է, իսկ սերվերում՝ null։ Կանոն՝ env()-ը միայն config/ ֆայլերում, իսկ մնացած տեղերում՝ config('app.name')։

Եվ .env-ը փոխելուց հետո սերվերում պետք է նորից գործարկել php artisan optimize, հակառակ դեպքում փոփոխությունը չի երևա։ Սա production-ի «ինչո՞ւ չի աշխատում» հարցերի առաջին պատճառն է։

04Հարձակում․ սխալ document root

Դաս 15-ում public/-ը դարձրինք միակ թղթապանակը, որը տեսանելի է ինտերնետից։ Այսօր տեսնում ենք, թե ինչ է կատարվում, երբ դա մոռացվում է սերվերում։

Document root = ~/technomarket (ՍԽԱԼ) https://site.am/ → ցուցակ կամ 403 https://site.am/public/ → կայքը աշխատում է ⚠️ «ամեն ինչ լավ է» https://site.am/.env → DB_PASSWORD=..., APP_KEY=... 💥 https://site.am/storage/logs/laravel.log → սխալներ, հարցումներ, email-ներ 💥 https://site.am/composer.json → բոլոր փաթեթները և տարբերակները Document root = ~/technomarket/public (ՃԻՇՏ) https://site.am/ → կայքը https://site.am/.env → 404 https://site.am/storage/... → միայն public/storage-ի symlink-ը (նկարներ)
ստուգիր քո demo-ն
curl -I https://technomarket.example.am/.env
# HTTP/2 404   ← ճիշտ

curl -I https://technomarket.example.am/storage/logs/laravel.log
# HTTP/2 404   ← ճիշտ

curl -I https://technomarket.example.am/composer.json
# HTTP/2 404   ← ճիշտ
Ինչու է սա այդքան տարածված

Էժան shared hosting-ում հաճախ document root-ը ֆիքսված է public_html-ի վրա և չի փոխվում։ Ամենապարզ «լուծումը», որը կգտնես ֆորումներում, ամբողջ նախագիծը public_html-ի մեջ գցելն է և .htaccess-ով վերահղելը public/։ Կայքը կաշխատի, բայց .env-ը մնում է հասանելի, եթե վերահղումը մեկ տեղ սխալ է։

Ճիշտ տարբերակը Դաս 15-ից է․ նախագիծը՝ public_html-ից դուրս, իսկ public_html-ում՝ միայն public/-ի պարունակությունը (կամ symlink)։ Եթե հոսթինգը թույլ չի տալիս ոչ մեկը, ոչ մյուսը, ընտրիր ուրիշ հոսթինգ։

Նկարները կարող են անհետանալ

Cloud ծառայություններում սերվերի ֆայլային համակարգը մշտական չէ․ ամեն deploy ստեղծում է նոր, մաքուր միջավայր։ Եթե Դաս 21-ի տնայինում նկարները պահում ես storage/app/public-ում, հաջորդ push-ից հետո դրանք կկորեն։

Լուծումը օբյեկտային պահոցն է (S3-համատեղելի, Laravel Cloud-ում կա որպես առանձին ռեսուրս) և FILESYSTEM_DISK-ի փոփոխությունը։ Demo-ի համար ավելի պարզ է demo նկարները պահել public/images-ում և commit անել դրանք։ Laravel-ի Storage-ը նույնն է մնում, փոխվում է միայն disk-ը։ Սա Դաս 13-ի ինտերֆեյսի գաղափարն է ֆրեյմվորքի մակարդակում։

README.md
# TechnoMarket

An Armenian-language electronics store built with Laravel 13 —
after first building the same app on a hand-written PHP MVC framework.

**Live demo:** https://technomarket.example.am
**Demo admin:** demo@technomarket.example.am / demo-password (manager role, cannot delete)

![Catalog and admin panel](docs/screenshot.png)

## Features

- Catalog with categories, search, pagination and discounts
- Session-based cart with AJAX updates (JSON API, 422 validation errors)
- Admin panel: product CRUD with soft deletes and unique Armenian slugs
- Authentication with Laravel Fortify, rate-limited login, no public registration
- Role-based authorization with Gates (admin / manager)
- Fully localized validation messages (hy)

## What I added beyond the course

- Product reviews with a Policy: one review per user per product
- Feature tests for the cart and admin authorization (Pest)

## Tech stack

PHP 8.3 · Laravel 13 · MySQL 8 · Blade · Fortify · vanilla JS · custom CSS

## Security decisions

| Threat | How it is handled |
|---|---|
| XSS | Blade escaping everywhere, no unescaped output |
| SQL injection | Eloquent / bound parameters only |
| CSRF | @csrf on every form, logout via POST |
| Mass assignment | `$fillable` + `validated()` only; `role` is not fillable |
| Brute force | Login throttled per email + IP |
| N+1 queries | Eager loading + `Model::shouldBeStrict()` in development |

## How it was built

1. Plain PHP with templates, sessions and PDO
2. A custom MVC framework: router, controllers, auth and CSRF checks, REST API
   → [technomarket-mvc](https://github.com/USERNAME/technomarket-mvc)
3. Rebuilt in Laravel — this repository

## Run locally

```bash
git clone https://github.com/USERNAME/technomarket-laravel.git
cd technomarket-laravel
composer install
cp .env.example .env
php artisan key:generate
php artisan migrate --seed
php artisan storage:link
php artisan serve
```

Default local admin: admin@technomarket.test / password (local only).
