Դաս 11-ում, երբ ապրանքները գան բազայից, հենց այս սցենարը հնարավոր կդառնա։

Բրաուզերն այժմ ստանում է &lt;script&gt;։ Դա տեքստ է, ոչ թեգ։

Օգտագործողը էկրանին տեսնում է ուղիղ այն, ինչ գրել է՝ <script>alert('XSS')</script> — որպես սովորական բառեր։ Կոդը չի կատարվում։

Ուշադրություն՝ մենք ոչինչ չենք ջնջում և չենք արգելում։ Օգտագործողը կարող է գրել ինչ ուզի — մենք պարզապես ասում ենք բրաուզերին․ «սա տեքստ է»։

ճիշտ պարամետրերով
htmlspecialchars($text, ENT_QUOTES | ENT_SUBSTITUTE, 'UTF-8')

// ENT_QUOTES      — փախցնում է և ' և " ⭐
// ENT_SUBSTITUTE  — վնասված UTF-8-ը փոխարինում է, ոչ դատարկում
// 'UTF-8'         — հայերենի համար պարտադիր
Ինչո՞ւ ENT_QUOTES

Առանց դրա մեկ չակերտը չի փախցվում։ Իսկ դա բավական է հարձակման համար՝

<input value='<?= $x ?>'> և $x = "' onfocus='alert(1)"

Արդյունքում ստացվում է աշխատող onfocus ատրիբուտ, առանց ոչ մի <script> թեգի։

PHP 8.1-ից ENT_QUOTES-ը լռելյայն է, բայց գրիր բացահայտ — կոդդ կաշխատի նաև հին սերվերում։

Օգնական ֆունկցիա

functions.php
function e(?string $text): string
{
    return htmlspecialchars($text ?? '', ENT_QUOTES | ENT_SUBSTITUTE, 'UTF-8');
}

Ինչո՞ւ մեկ տառ

Որովհետև այն գրելու ես հարյուրավոր անգամ։ Երկար անունը ստեղծում է գայթակղություն՝ բաց թողնել «այս մեկ տեղում»։

Laravel-ում կա նույն ֆունկցիան՝ ճիշտ նույն անունով e()։ Blade-ում {{ $x }}-ը ավտոմատ կանչում է այն։ Դաս 19-ում այդ մասին։

Կանոն՝ բոլոր տվյալները, որոնք եկել են դրսից, անցնում են e()-ով։ Առանց բացառությունների։

Ամենահաճախ բաց թողնվող դեպքը

Ատրիբուտն առանց չակերտների։ e()-ն այնտեղ չի փրկում, որովհետև բացատը բավական է նոր ատրիբուտ սկսելու համար՝

$x = "x onerror=alert(1)" → <img alt=x onerror=alert(1)>

Կանոն՝ ամեն ատրիբուտի արժեք միշտ չակերտների մեջ։ Դա նաև HTML-ի վալիդության պահանջ է։

JS-ի ներսում e()-ն սխալ է

<script>-ի ներսում HTML-ի կանոնները չեն գործում։ e()-ն այնտեղ և՛ չի պաշտպանում, և՛ փչացնում է տվյալները՝ &quot;-ը կմնա տեքստում։

json_encode-ը ճիշտ գործիքն է․ այն արտադրում է վավեր JS արժեք և փախցնում է ամեն վտանգավոր նիշ։

JSON_UNESCAPED_UNICODE-ը պետք է, որ հայերենը մնա ընթեռնելի, ոչ \u0531 ձևով։

Հինգերորդ դեպքը՝ href և src

Առաջին չորս դեպքերում հարձակումը պահանջում էր հատուկ նիշեր՝ <, ", '։ Այստեղ այն ոչ մի հատուկ նիշ չի պահանջում։

❌ e()-ով, բայց էլի խոցելի

<a href="<?= e($brand['site']) ?>">Արտադրողի կայքը</a>

// Հարձակվողը ադմին վահանակում գրում է՝
//   javascript:alert(document.cookie)
// e()-ից հետո՝ ՆՈՒՅՆԸ։ Մեկ հատուկ նիշ էլ չկա։

<a href="javascript:alert(document.cookie)">Արտադրողի կայքը</a>
Սեղմելիս սկրիպտը կատարվում է քո կայքի անունից

e()-ը փախցնում է նիշեր, իսկ javascript:-ը սովորական տառեր են՝ երկու կետն ու փակագծերը չեն փոխարինվում։

Արդյունքը՝ նույն Stored XSS-ը, ինչ <script>-ով․ ուղղակի օգտագործողը պետք է սեղմի հղումը։ Նույն վտանգը կա data: և vbscript: սխեմաների հետ։

Սա հիմնական պատճառն է, որ «միշտ e()» կանոնը անբավարար է։ Ամբողջ հասցեի համար պետք է ստուգել սխեման։

✅ functions.php — սպիտակ ցուցակ
function safeUrl(?string $url, string $fallback = '#'): string
{
    $url = trim($url ?? '');

    if ($url === '') {
        return $fallback;
    }

    // Ներքին հասցե՝ /contact, բայց ոչ //evil.com ⭐
    if (str_starts_with($url, '/') && !str_starts_with($url, '//')) {
        return $url;
    }

    $scheme = strtolower((string) parse_url($url, PHP_URL_SCHEME));

    return in_array($scheme, ['http', 'https', 'mailto', 'tel'], true)
        ? $url
        : $fallback;
}

// Օգտագործում՝ երկուսը միասին
<a href="<?= e(safeUrl($brand['site'])) ?>">Արտադրողի կայքը</a>
Սպիտակ ցուցակ, ոչ արգելքների ցուցակ

Գայթակղիչ է գրել str_contains($url, 'javascript:') և արգելել։ Դա շրջանցվում է․ բրաուզերները URL-ի ներսից անտեսում են tab-ը և նոր տողը, ուստի java&#9;script:alert(1) նույնպես աշխատում է։

Հակառակ մոտեցումը չի շրջանցվում․ թույլատրիր միայն հայտնի սխեմաները, մնացած ամեն ինչ վերածվում է #-ի։ Անծանոթ ձևը պարզապես չի անցնում։

//-ի ստուգումը նույնն է, ինչ Դաս 7-ի բաց վերահղման դեպքում․ //evil.com-ը սկսվում է շեղագծով, բայց արտաքին հասցե է։ Նույն տվյալը, երկու տարբեր վտանգ։

04Ե՞րբ փախցնել

Երկու հնարավոր ռազմավարություն ❌ Փախցնել ՄՈՒՏՔԻ ժամանակ Բազայում պահվում է &lt;script&gt; · Տվյալները աղավաղված են · API-ում կստացվի սխալ JSON · Կրկնակի փախցնելիս՝ &amp;lt; · Չես կարող փոխել ելքի ձևաչափը ✅ Փախցնել ԵԼՔԻ ժամանակ Բազայում պահվում է <script> ինչպես կա · Տվյալները մաքուր են · HTML-ի համար՝ e() · JSON-ի համար՝ json_encode() · PDF-ի, էլ. նամակի համար՝ իր ձևը
Կանոն

Վալիդացիա՝ մուտքի ժամանակ։ Փախցնում՝ ելքի ժամանակ։

Մուտքում ստուգում ենք՝ էլ. հասցեն վավե՞ր է, տարիքը թի՞վ է, տեքստը շատ երկար չէ՞ (Դաս 6)։

Ելքում որոշում ենք, թե ինչպես ապահով ցուցադրել՝ կախված համատեքստից։

Այս բաժանումը կարևոր է, որովհետև նույն տվյալը կարող է գնալ և՛ HTML, և՛ JSON, և՛ էլ. նամակ — երեք տարբեր փախցնում։

05Շաբլոնների համակարգ

Ընթացիկ մոտեցման խնդիրը

Դաս 3-ում սովորեցինք՝ ֆունկցիաները չեն տեսնում արտաքին փոփոխականները, իսկ include-ով միացված շաբլոնը աշխատում է render()-ի ներսում։ Փոփոխականը կհասանելի չլիներ, հաստատունը՝ ամենուր է։

06render() ֆունկցիան

Ինչպե՞ս ստանալ շաբլոնի արդյունքը որպես տող։

functions.php
function render(string $view, array $data = []): string
{
    extract($data);          // ['title'=>'X'] → $title = 'X'

    ob_start();               // սկսում ենք հավաքել ելքը
    require __DIR__ . "/views/{$view}.php";
    return ob_get_clean();     // վերադարձնում ենք հավաքածը
}
Ինչպես է աշխատում ob_start() ob_start() │ PHP-ն դադարում է ուղարկել ելքը բրաուզերին │ և հավաքում է այն բուֆերում │ require 'views/pages/home.php' │ Շաբլոնը «տպում» է HTML — բայց այն գնում է բուֆեր │ ob_get_clean() │ Վերցնում ենք բուֆերի պարունակությունը որպես տող │ և մաքրում բուֆերը ▼ Ստանում ենք HTML-ը փոփոխականում

Ինչո՞ւ $content-ը չի անցնում e()-ով

Որովհետև այն արդեն HTML է, և ոչ օգտագործողի տվյալ։ Այն մենք ենք գեներացրել՝ արդեն փախցնելով ամեն ներսի արժեք։

Դա միակ տեղն է, որտեղ e()-ն բացակայում է դիտավորյալ։ Ուշադիր եղիր՝ $content-ի մեջ երբեք չպիտի ընկնի չփախցված օգտագործողի տվյալ։

Laravel-ում նույն տարբերությունը կա՝ {{ $x }} փախցնում է, {!! $x !!}՝ ոչ։ Երկրորդը օգտագործվում է հազվադեպ և միշտ գիտակցաբար։

Ի՞նչ ձեռք բերեցինք

1. Layout-ը ամբողջական վավեր HTML է
2. Էջերի ֆայլերը պարունակում են միայն բովանդակություն
3. Տվյալները փոխանցվում են բացահայտ՝ render()-ի երկրորդ արգումենտով
4. Նոր էջ ավելացնելը՝ մեկ ֆայլ views/pages/-ում

Սա արդեն MVC-ի սաղմն է․ index.php-ը կոնտրոլերն է, views/-ը՝ V-ն, data.php-ը՝ M-ի տեղը։ Դաս 15–17-ում այն կդառնա լիարժեք։

Այս render()-ի երկու թույլ տեղը

Սա դիտավորյալ պարզ տարբերակ է։ Այն երկու խնդիր ունի, որ հիմա չենք լուծում, բայց պետք է իմանալ․

1. extract($data)-ը վերագրում է ցանկացած փոփոխական։ Եթե $data-ում լինի բանալի 'view', այն կվերագրի render()-ի սեփական պարամետրը, և require-ը կփնտրի սխալ ֆայլ։

2. Շաբլոնում սխալ լինելու դեպքում բուֆերը մնում է բաց։ Եվ սխալի էջը կհայտնվի կիսատ <div>-ների մեջ։

Երկուսն էլ կուղղվեն Դաս 15-ում՝ EXTR_SKIP և ob_end_clean() catch-ում։ Այդ ժամանակ կհասկանաս, թե ինչու են դրանք այնտեղ։

08Տնային աշխատանք

Մինի-նախագիծ

Այս տնայինի գլխավոր մասը՝ «Շաբլոններ և XSS», Անիի գրքերի ակումբում՝ քայլ առ քայլ, starter ֆայլերով և պատրաստի օրինակով։ Ներքևի ցուցակի կետերը, որ նշված չեն որպես «մինի-նախագծում», կատարիր ՏեխնոՄարկետում։

  1. Կատարիր դասարանականի 8 քայլը։
  2. Ցուցադրիր XSS-ը երկու սքրինշոթով՝ առանց e()-ի և դրանով։
  3. Փորձարկիր հինգ տարբեր payload՝ <script>, <img onerror>, <svg onload>, javascript: հղումում, ' onfocus=' ատրիբուտում։ Որո՞նք են աշխատում առանց e()-ի։
  4. Ցուցադրիր ատրիբուտի խնդիրը՝ չակերտներով և առանց դրանց, e()-ի հետ միասին։
  5. Ստեղծիր երրորդ էջ՝ about.php, նույն layout-ով։ Քանի՞ տող կրկնեցիր՝ համեմատած Դաս 3-ի partials/ մոտեցման հետ։
  6. Ավելացրու $title-ը ամեն էջի համար։
  7. Բացատրիր սեփական բառերով, ինչու փախցնում ենք ելքի, ոչ մուտքի ժամանակ։
  8. Ցուցադրիր, ինչ է լինում, երբ e()-ն կիրառում ես երկու անգամ նույն տողի վրա։
  9. Օգտագործիր json_encode-ը <script>-ի ներսում հայերեն տեքստի հետ։ Համեմատիր JSON_UNESCAPED_UNICODE-ով և առանց դրա։
  10. Խնդրիր AI-ին վերանայել քո շաբլոնները և գտնել բաց թողնված e()-երը։ Ուղղիր ինքդ։

Շաբլոնների կառուցվածքը

index.php → տվյալներ + render() views/layout.php → ամբողջական HTML կմախք views/pages/*.php → միայն բովանդակություն render($view, $data) extract($data) → զանգվածը դառնում է փոփոխականներ ob_start() → սկսում ենք հավաքել require $view → շաբլոնը տպում է բուֆեր ob_get_clean() → վերադարձնում ենք որպես տող

Կանոններ

· Վալիդացիա՝ մուտքի ժամանակ · Փախցնում՝ ելքի ժամանակ · e() ամեն դրսից եկած արժեքի վրա · Ատրիբուտները միշտ չակերտների մեջ · JS-ի ներսում՝ json_encode, ոչ e() · Հասցեների համար՝ սխեմայի սպիտակ ցուցակ

Ստուգաթերթ

  • Կա e() ֆունկցիան ENT_QUOTES-ով
  • Բոլոր օգտագործողի տվյալները անցնում են e()-ով
  • Բոլոր ատրիբուտները չակերտների մեջ են
  • Layout-ը ամբողջական վավեր HTML է
  • Էջերի ֆայլերում չկա <html>, <head>
  • Փորձարկել եմ վտանգավոր payload-ով
  • Ամեն href և src, որ գալիս է տվյալներից, անցնում է safeUrl()-ով
  • SITE_NAME-ը սահմանված է
  • Բազայում պահվում են մաքուր տվյալները

Ինքնաստուգում

  • Կարո՞ղ եմ բացատրել, ինչու է XSS-ը վտանգավոր
  • Գիտե՞մ Stored և Reflected XSS-ի տարբերությունը
  • Հասկանո՞ւմ եմ, ինչու ENT_QUOTES
  • Գիտե՞մ, ինչու JS-ի ներսում e()-ն սխալ է
  • Կարո՞ղ եմ բացատրել ob_start()-ի աշխատանքը
  • Գիտե՞մ, ինչու e()-ը չի պաշտպանում href="javascript:..."-ից
  • Կարո՞ղ եմ բացատրել, ինչու սպիտակ ցուցակը ավելի ապահով է, քան արգելքների ցուցակը
Հաջորդ դասին

Ֆորմաներ և վալիդացիա — անվտանգության երկրորդ դասը։ Կկառուցենք կոնտակտների ֆորմա սերվերային ստուգմամբ և վերջապես կհասկանանք գործնականում, ինչու HTML Դաս 4-ի required-ը անվտանգություն չէ։

Կսովորենք նաև filter_var-ը, սխալների ցուցադրումը դաշտերի կողքին և լրացրած արժեքների պահպանումը։
